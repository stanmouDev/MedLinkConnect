# MedLink Connect — Offline-First Audit Report

**Date:** 2026-07-12
**Scope:** Frontend PWA (`frontend/src/**`) and backend Django REST API (`backend/**`)
**Verdict:** ❌ **NOT truly offline-first.** The product is an online-only SPA wrapped in a PWA shell. It can *load* without a network but cannot *capture, read, or sync* clinical data offline. The README itself states: "the backend must be running for the app to work."

---

## Findings by Capability

### 1. Local database / on-device data store
- **Status: MISSING**
- No `IndexedDB`, `localForage`, `idb`, or any client-side database exists anywhere in `frontend/src` (full grep returned zero matches).
- Every list/read (`api.list`) and write (`api.create/update/remove`) in `src/api.ts` goes **directly to the Django REST API** via `fetch`. There is no read-through cache.
- Consequence: with no backend, the app shows no patient data and cannot register/save anything. A clinician with no signal cannot open a previously viewed chart.

### 2. Service Worker
- **Status: PARTIAL / cosmetic**
- A SW is registered in `src/main.tsx` (`registerSW({ immediate: true })`) and generated by `vite-plugin-pwa` (`frontend/dist/sw.js`).
- However, the SW **only precaches the app shell** (`index.html`, JS, CSS, `manifest.webmanifest`) via Workbox. It implements no runtime caching of API responses and no queueing of POST/PUT requests.
- Net effect: offline **app shell loading only** — not offline data.

### 3. IndexedDB usage
- **Status: MISSING** (see #1). The architecture doc (`docs/architecture.md:18`) *claims* "Offline storage: IndexedDB in browser with encrypted local payloads" — this is aspirational; the code does not implement it.

### 4. Local asset hosting
- **Status: PRESENT (build artifact only)**
- The PWA manifest and precached assets exist in `frontend/dist/`, enabling installable, offline-loadable UI.
- Caveat: `vite.config.ts` references `pwa-192x192.png`, `pwa-512x512.png`, `favicon.ico`, `apple-touch-icon.png`, `masked-icon.svg` — these are not present in `frontend/public`/source, so the manifest icons will 404 in production.

### 5. Offline synchronization
- **Status: MISSING (foundation only)**
- The backend has a `SyncRecord` model (`backend/medlink_backend/models.py:111`) and a `/api/sync-records/` CRUD endpoint (`SyncRecordViewSet`), and `docs/api.md:22` says sync records "queue changes for later reconciliation."
- **Nothing in the frontend ever creates, stores, or drains a `SyncRecord`.** There is no outbox queue, no write-back when connectivity returns, and no pull of server changes. The `sync` Django app (`backend/sync/`) is an **empty stub** (`models.py`/`views.py` are blank).
- No `updated_at`-based delta pull exists, even though most models carry an `updated_at` field that could anchor replication.

### 6. Conflict resolution
- **Status: MISSING**
- No version vectors, ETags, `updated_at` comparison, last-write-wins policy, or manual-merge UI anywhere. Writes are blind `PUT`/`POST` to the server. Concurrent edits by two offline clinicians would silently overwrite each other.

### 7. Automatic sync after connectivity restored
- **Status: MISSING**
- No `navigator.onLine` / `online` event listener, no Background Sync API registration, no retry/backoff queue. The app has no awareness of connectivity state at all (grep for `onLine`/`online`/`offline` in `frontend/src` = zero matches).
- There is no UI indicator of "pending changes" or "reconnecting."

## Component Gap Summary

| Component | Required for offline-first | Present? | Notes |
|---|---|---|---|
| Client-side DB (IndexedDB) | Yes | ❌ | No local store at all |
| Read-through cache | Yes | ❌ | All reads are live API |
| Write outbox / mutation queue | Yes | ❌ | No queueing of offline writes |
| Service Worker (data) | Yes | ⚠️ | Shell precache only |
| Delta sync (pull since `updated_at`) | Yes | ❌ | `updated_at` exists but unused |
| Conflict resolution | Yes | ❌ | None |
| Auto-sync on reconnect | Yes | ❌ | No connectivity awareness |
| Local asset hosting | Yes (PWA) | ⚠️ | Icons missing in source |
| Encrypted local payloads | Claimed | ❌ | Claimed in docs, not implemented |

## Recommendations (prioritized)

1. **Add a client-side store + outbox (highest impact).** Introduce `Dexie`/`localForage` (IndexedDB). Maintain a local mirror of each entity and an outbox table of pending mutations (`{entity, id, op, payload, status, createdAt}`).
2. **Make reads offline-capable.** Convert pages (`Patients.tsx`, `Encounters.tsx`, etc.) to read from the local store first, then hydrate from the API. Prefer a library like `rxdb` or a thin repository layer.
3. **Implement write-queuing.** `api.create/update/remove` should (a) apply optimistically to IndexedDB + outbox, and (b) flush the outbox to `/api/sync-records/` when online.
4. **Build a real sync engine in the `sync` app.** Replace the empty `backend/sync/` stub with:
   - `POST /api/sync/push` accepting a batch of outbox items; server applies with ownership/role checks.
   - `GET /api/sync/pull?since=<timestamp>` returning entities changed after `since` (leverage existing `updated_at` fields).
   - Token-based watermark/`last_sync` per device/user.
5. **Add conflict resolution.** Add a `version`/`updated_at` (or vector clock) per entity. On push, reject stale writes and surface a merge/override prompt in the UI rather than silently overwriting.
6. **Wire auto-sync on reconnect.** Use `window.addEventListener('online', …)` plus the **Background Sync API** (`workbox-background-sync`) to flush the outbox. Show a "pending N changes / synced" banner.
7. **Encrypt at rest.** Implement the AES-256 "encrypted local payloads" the docs promise (e.g., Web Crypto derived key, per-device key) for PHI stored in IndexedDB.
8. **Fix PWA assets.** Add the referenced `pwa-192x192.png`, `pwa-512x512.png`, etc. to `frontend/public` so the manifest is valid.
9. **Correct the documentation/marketing.** Either implement the above or soften the "offline-first" and "encrypted local storage" claims in `README.md` and `docs/architecture.md` to reflect current state.

---

## Bottom Line
MedLink Connect is architected as an **online-only client** with PWA scaffolding. The offline data path (local DB, outbox, sync engine, conflict resolution, reconnect sync) is **entirely absent** despite being described in the docs. Before it can serve clinics with intermittent connectivity, items 1–6 must be built; the backend `SyncRecord` model is a good starting point but is currently unused dead code.
